# platforms/video — k2bink and the movie player

k2bink is a Bink 1 decoder (revisions d and f–i) in C99 with no dependencies. It is a C port of
[unbikit](https://github.com/blennies/unbikit) (MIT OR Apache-2.0, see `k2bink/LICENSE.unbikit.md`),
with the corrections listed below. **k2movie** is the player built on it: it is the engine's
`ASL::PlayBinkMovieGL` (`docs/MIDDLEWARE_REPLACEMENT.md` §3), and the root `CMakeLists.txt` links it
into `k2` through `k2_platform`. Until the engine gets far enough to start a movie, the host
tools here are the test bed.

```sh
cmake -S platforms/video -B platforms/out/video -G Ninja && cmake --build platforms/out/video
platforms/out/video/binkcheck decomp_bins/swkotorii_switch/romfs/Movies/*.bik   # headless, vs ffmpeg
platforms/out/video/binkplay  decomp_bins/swkotorii_switch/romfs/Movies/Aspyr.bik
SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy platforms/out/video/binkplay <movie>  # headless pacing test
platforms/out/video/binkgl    decomp_bins/swkotorii_switch/romfs/Movies/Aspyr.bik   # the engine entry point
platforms/out/video/binkgl --verify 30 --hidden decomp_bins/swkotorii_switch/romfs/Movies/*.bik
```

ffmpeg is a **dev-time oracle only**. It runs as a separate process through a pipe, and nothing
links it or ships it.

## Where k2bink deliberately differs from unbikit

Each of these was found by `binkcheck` and verified against ffmpeg and the original binary:

* **Quantizer tables.** unbikit scales one base matrix by float factors, which is off by up to 22
  at the high levels. The result is sparse ±1 pixel errors in every movie. The real tables are
  static data in the Bink SDK: `libkotor2.so` (arm64) has inter at `0xa08b80` and intra at
  `0xa09b80`, each 16 levels × 64 int32 in natural order. They are read by the fused dequant+IDCT
  routines `FUN_00936cf8` and `FUN_0093705c`. All 2,048 values equal ffmpeg's.
* **DCT audio gain.** unbikit multiplies by `4·base`. At 2,048-sample frames (44.1/48 kHz) that is
  4√2 too loud, and KOTOR's movies peak at about 5.5. The error depends on frame length, so at
  1,024 samples (32 kHz) it is off by a different factor. The inverse DCT's normalization is `2/N`,
  and k2bink uses that.
* **DCT audio precision.** Lee's recursive DCT multiplies by `0.5/cos(≈π/2)`, about 650 at N=2048,
  next to the middle output. In float that exceeds 1 LSB, so k2bink runs the transform in double.
* **Plane buffers.** k2bink keeps padded planes (an extra block right and below) and walks blocks
  by explicit row/column position. unbikit uses stride = width and a running pointer, which is only
  correct when the width is a multiple of 8.
* **Robustness.** Bundle writes, run lengths and motion-vector references are bounds-checked and
  return `K2BINK_ERR_FORMAT`. unbikit relies on JS typed-array semantics.

**Provenance.** unbikit is reference-informed by FFmpeg (see the finding in
`docs/MIDDLEWARE_REPLACEMENT.md` §3). As decided there, the routines that tracked FFmpeg statement
by statement were re-derived in k2bink's own structure:

* bundle refill;
* explicit-order tree;
* the coefficient work-queue;
* the colour context;
* the IDCT;
* the audio band reader;
* the audio crossfade.

## Untested paths

KOTOR II's movies are all revision `i`, 1920×1080 or smaller, with no alpha and DCT stereo audio.
These paths are ported but have never run against real data:

* alpha planes;
* grayscale;
* revisions below `i`, including the colour sign-flip and the non-swapped U/V order;
* RDFT audio;
* more than 2 channels.

Bink 2 and revisions `b`, `c` and `e` return `K2BINK_ERR_UNSUPP`. That is the same set unbikit
supports.

## The player (`player/`)

Behaviour comes from Aspyr's two players, read in Ghidra:

* **Android `MacPlayBinkGL` @`0x889b7c`** (the target):
  * a skip lands only once one second of video is on screen (Bink frame number > the integer fps);
  * subtitles are drawn at `frame / fps`;
  * the movie pauses while the window has lost focus.
* **macOS `ASL::PlayBinkMovieGL` @`0x10048130e`** (the desktop reference):
  * the argument meanings: arg 3 is the Bink sound track, arg 4 (the engine's 250) is how long input
    is ignored, `*pbOut` is the **skip** flag (the engine's `m_nUnk20`, not "did it start"), and
    arg 6 is the quit flag;
  * the event filter: every event is swallowed while the movie runs, and a key, mouse, joystick,
    controller or finger **release** is a skip;
  * the shader and its Bink 1 colour constants, `Setup_Bink_shaders()::bink1_consts`
    @`0x10050b140` (BT.601 limited range);
  * aspect-fit into the window, and GL state saved and restored around the movie.

**Deliberate differences:**

* Window events pass through the filter, so the engine still sees resizes.
* An `SDL_QUIT` ends the movie at once, and is re-posted afterwards so the engine sees it.
* Audio goes to its own SDL audio device, not the engine's mixer. When the FMOD→miniaudio shim
  (§1) lands, it moves onto that shim's `ma_engine`, as the plan says.

**Verified (2026-09-30, `binkgl` on an M1 Max, GL 2.1 Metal):**

* **Pixels.** `--verify 30` passes all 88 movies. Worst channel error is 1 against the CPU model,
  and GL state is restored every time.
* **Skip rules.** A release at 100 ms is dropped (inside the 250 ms delay). One at 500 ms is held
  and lands at the one-second mark (1.12 s wall). One at 1,500 ms ends at 1.58 s.
* **Pacing.** Silent playback runs on the wall clock (9.25 s for a 9.24 s movie). Audio playback
  on CoreAudio overshoots by a constant ~0.27 s of device start-up and does not drift (4.28 s for
  4.00 s, 21.18 s for 20.92 s). SDL's dummy audio driver consumes about 3% slow, so do not judge
  pacing with it.

**Not yet exercised in the engine.** `k2` links the player, but the engine does not reach a
movie yet: no window or GL context exists until the Win32/ASL shim layer is written. It plays into
the context current on the calling thread; on a thread without one (the engine's
`AsyncPlayThreadProc` path) it reports "did not open" and returns at once.
